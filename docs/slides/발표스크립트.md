## p4 · 과제 배경 | 해결되지 않은 문제 — 2분

**이 장의 목적** — ① 사람이 직접 하고 있다 ② 기존 비서로는 안 된다, 두 가지를 각인시키는 것

### 강조 1 — 숫자로 시작
- ▶ **미팅 일정 조율 한 건에 평균 7.3회 왕복.** 청중이 바로 체감하는 숫자라 여기서 한 박자 쉬어줍니다.
- 이어서 "이게 쌓여서 **결정 피로**가 되고, 결국 늘 가던 데로 정하는 질 낮은 선택이 반복된다"로 연결.

### 강조 2 — 부담이 심해지는 두 상황
- **다수 의견 조율 시** — 참여자가 늘면 메시지 왕복 비용이 급증
- **개인 민감 정보 포함 시** — 일정·건강·선호 데이터라 클라우드로 넘기기도, 남에게 주기도 어려움

### 강조 3 — 기존 AI 비서의 한계
- ▶ **"단일 사용자 + 명령 대기" 구조.** 이 표현 하나로 정리됩니다.
- 내가 시켜야 움직이고(Reactive), 내 컨텍스트 안에서만 돌고, **협상·합의 기능 자체가 없음**

### 마무리
- 💬 "필요한 건 세 가지입니다. **명령하지 않아도 의도를 먼저 읽는 능력, 상대와 자율적으로 협의해 결과만 가져오는 능력, 그리고 그걸 On-device에서 처리하는 능력**입니다."
- 하단 문구 그대로 — 💬 "**협상은 On-device AI가, 결과만 나에게.**"

> ⚠ 주의 — 여기서 말한 "의도를 먼저 읽는 능력"은 IDS 영역입니다. 확정된 FR·QA·DP는 **협상(MAF) 쪽만** 다루므로, 뒤에서 "이번에 검증한 건 협상 부분"이라고 한 번 선을 그어주는 편이 안전합니다.

- 💬 "그런데 당사 Agent는 그걸 알 수 있습니다. **스마트폰에서 일정·연락처·이동 패턴을, TV와 가전에서 생활 루틴과 사용 패턴을** 봅니다."

### 강조 2 — 경쟁사 대비

- ▶ **당사는 스마트폰·TV·가전 전체 통합이 이미 완성된 유일한 사업자**

## p7 · 과제 개요 | 무엇을 만드는가 — 1분 30초

**이 장의 목적** — 시스템 구조 두 덩어리 + 목표 한 문장 + 4대 케이스 중 **어디를 다루는지**

### 강조 1 — 구성은 두 덩어리
- **IDS** — 디바이스 컨텍스트를 모니터링해 사용자의 명시적·비명시적 Intent를 능동 감지
- **MAF** — 감지된 Intent를 받아 Agent를 동적으로 구성하고, 상대방 Agent와 자율 협상 수행
- 흐름 그대로 — 사용자 행동 → IDS 감지 → Task 생성 → MAF 협상·실행 → 결과 전달

### 강조 2 — 목표 한 문장 (또박또박)
- 💬 "**사용자의 AI Agent가 상대방 Agent와 자율 협상하여, 일상의 미세 의사결정에서 발생하는 인지 부하를 제거한다.**"

### 강조 3 — 4대 Communication Cases, 그리고 범위 선언
- Negotiation(협상) / Collaboration(협력) / Knowledge Sharing(지식 공유) / Remote Monitoring(원격 모니터링)
- 각 케이스는 예시 한 줄씩만 — 저녁 약속 협상 / 보고서 분담 작성 / 선호·경험 정보 공유 / 고령자 긴급 상황 통보
- ▶ **가장 중요:** "이 중 **이번 과제에서 다루는 것은 Negotiation**입니다. 뒤에 나올 품질 속성과 설계 문제도 전부 협상을 대상으로 합니다."

> ⚠ 이 선언을 빠뜨리면 "네 가지를 다 만들었느냐"는 질문이 반드시 들어옵니다.

→ "그럼 요구사항을 어떻게 수집하고 정제했는지로 넘어가겠습니다."

## p14 · 설계 Overview — 1분 20초

**이 장의 목적** — 설계 문제가 **두 개뿐**이고, 그것이 **모듈 뷰 어디에 있는지** 짚기

### 강조 1 — 문제는 두 개
- ▶ **협상 시 메모리** → 복합 이슈 협상의 후보군을 어떻게 구성할 것인가 → **DP1**
- ▶ **협상 결과 정확성** → 다자간 협상을 어떻게 설계할 것인가 → **DP2**
- 💬 "앞서 본 QA2가 DP1으로, QA1이 DP2로 내려온 것입니다."

### 강조 2 — 색으로 위치 짚기 (손으로 가리키며)
- 💬 "Personal Proxy Agent 안의 **Negotiation Engine**이 실제 협상이 도는 자리입니다."
- ▶ **빨간 영역 = DP1** — Issue Dispatcher, Candidates Builder (이슈를 나누고 후보군을 만드는 곳)
- ▶ **파란 영역 = DP2** — Lifecycle Manager, Session Manager, NegMAS (세션과 라운드를 관리하는 곳)
- 나머지 모듈(Sub Agent Dispatcher, Peer Discovery, Connection Manager, Inference Engine)과 외부(LLM Server, Message Server, 상대 단말)는 이름만 훑고 넘어갑니다.

→ "DP를 설명하기 전에, 협상 엔진으로 쓴 NegMAS를 먼저 짚고 가겠습니다."

## p15 · DP 사전 배경 — NegMAS를 이용한 협상 — 1분 40초

**이 장의 목적** — 협상이 실제로 어떻게 도는지 **한 번은 끝까지 따라가 보여주기.** 여기가 이해되면 DP1·DP2가 쉬워집니다.

### 먼저 한 줄 정의
- 💬 "**NegMAS는 에이전트 간 자동 협상 — 제안·거절·양보·합의 — 을 만들기 위한 오픈소스 협상 프레임워크**입니다."

### 강조 1 — 판을 먼저 설명
- 양쪽 Agent는 **후보마다 점수**를 갖고, **수락 기준선인 Threshold**를 갖습니다. (내 0.5 / 친구 0.6)
- ▶ **가장 중요:** "그런데 **이 점수표는 서로 보지 못합니다.**" — 여기서 한 박자 쉽니다. QA4가 왜 어려운 문제인지가 이 한마디에 걸려 있습니다.

### 강조 2 — 3라운드를 리듬 있게
- ① "금요일 7시 파스타" — 내 0.9, 최선. 친구 0.3 → **거절**
- ② "토요일 6시 김치찌개" — 친구 0.9. 내 0.4 → **거절**
